# 千万行级 C/C++ 电信系统的 Review 上下文方案：预建索引 + 分层 Memory 设计

> **快照说明（2026-08-17）**：本文自 open-code-review 仓库 `papers/` 拷入，作为 navmap 设计文档（`docs/navmap-libclang-extractor-design.md`）的上位依据留存参考。本文的演进主场仍在 open-code-review 仓，本副本不维护、可能滞后；navmap 侧设计变更只更新本仓的 navmap 设计文档。

> 整理日期：2026-08-16。背景：目标代码库为**千万行级 C/C++ 电信系统**，宏观架构稳定、单次 review 的 diff 很小（几十到几百行）。本文回答一个问题：review agent 的上下文获取，如何在 mcp-language-server 式动态提取、clangd 凌晨预建索引、code-review-graph（下称 CRG）式结构图、以及 memory 固化机制之间做取舍与组合。

## 0. 结论速览

- **索引引擎**：clangd（`clangd-indexer` + 静态索引）是主力，不可替代。tree-sitter 路线（CRG）在电信 C/C++ 上解不动宏分发/函数指针/条件编译，只能作备胎或非 C/C++ 部分的补充。
- **架构机制**：CRG 验证过的工程模式——文件 hash 增量失效、预计算摘要表、MCP 投递、impact radius 查询——直接借用。即"索引引擎换 clangd，上层架构抄 CRG"。
- **Memory 分层摘要**在千万行级是刚需而非优化：token 花费与仓库总量解耦的唯一手段。
- **导航图层**（消息分发表/状态机表/全局变量读写清单）是 LSP 单查询给不出来、review 又高频需要的蒸馏产物，自动化提取后固化，把 LSP 从"探索工具"变成"核对工具"。
- **最大风险**是 `compile_commands.json` 的生成与覆盖率（电信定制构建系统），必须最先验证。

## 1. 三种机制的角色划分

### 1.1 LSP 动态提取（mcp-language-server 模式）

- 精确到符号级，有编译器前端背书，永远新鲜。
- 代价：每个语言要部署对应 language server；大仓库冷启动索引慢；CI 容器里配齐多语言 LSP 不现实。
- 结论：作为**查询接口形态**保留（review 机器上跑 clangd 加载预建索引，对外走 LSP），但不承担索引构建职责。

### 1.2 凌晨预建索引（clangd 后台索引模型的工业化）

核心思想：**离线建、在线查**。昂贵的编译级解析放凌晨定时任务，产物是序列化索引分片；review 时只是读盘加载。

量级估算（按 LLVM 约 400 万行：全量索引约 1 小时、GB 级，外推）：

- 千万行级全量 `clangd-indexer`：数小时、数 GB 到十几 GB 索引 —— 凌晨窗口可行。
- **增量靠分片合并，不每晚全量**：索引按 TU（编译单元）分片，仅对 hash/mtime 变化的 TU 重跑 indexer 再合并 shard。电信系统日变更占比通常远小于 1%，增量构建十几分钟级。

### 1.3 Memory 固化

- 一次生成、多次复用，可入库版本化、可 CI 缓存共享。
- 承载图表达不了的**叙述性知识**：分层约定、设计意图、"所有 DB 访问必须走某封装"类红线。
- 前提：必须带失效机制与来源标注，否则陈旧上下文比缺上下文更糟（LLM 无条件信任注入内容，被带偏后错得更自信）。

## 2. 为什么 tree-sitter 路线不能当主力

电信 C/C++ 的典型特征恰好全打在 tree-sitter 启发式提取的盲点：

| 特征 | tree-sitter 的问题 | clangd 的表现 |
|---|---|---|
| 宏驱动分发（消息处理表、X-Macro 注册、状态机表） | 看到的是宏名，看不到展开后的调用边 | 宏展开后由编译器前端给出真边 |
| 函数指针 + 消息分发表（协议栈层间调用） | 无类型解析，连不出边 | 类型解析后可定位注册点与目标 |
| 条件编译（多产品形态/局向变体） | `#ifdef` 内代码要么全收（错）要么全丢（缺） | 按具体编译配置给出该变体下的真实视图 |

CRG 的 resolver 层（jedi/tsconfig 等）对 Python/TS 有缓解，但对 C/C++ 的上述场景无能为力。因此对 C/C++：图的 impact radius 若来自 tree-sitter，只能当"可能相关"候选集，不能当事实注入 prompt。

## 3. 编译变体问题（必须正面回答）

电信代码多形态编译，索引只能覆盖某个具体 `compile_commands.json` 对应的宏组合：

- 主索引选**覆盖被审代码最多的变体**；
- 若有 2~3 个差异巨大的主力形态，建多份索引，review 时按模块归属选用；
- 糊弄过去的后果：索引里是一批"错误的真相"，比没有更危险。

## 4. Memory 分层设计

千万行代码无人能全记住，且电信系统架构稳定、接口演化慢，memory 陈旧速度远慢于一般互联网项目，固化收益极高：

| 层级 | 内容 | 生成方式 | 失效策略 | 变化周期 |
|---|---|---|---|---|
| L1 子系统级 | 信令面/媒体面/OAM 职责、边界、对外接口 | 人工撰写/review 后入库 | 版本化，随架构演进人工更新 | 年 |
| L2 模块级 | 模块内消息流、状态机、关键全局数据结构 | LLM 生成 + 人工把关入库 | 人工评审驱动更新 | 月 |
| L2.5 导航图 | 消息分发表、状态机表、全局变量读写清单（见 §5） | 索引 + AST 自动提取，人工抽检 | 按基线 commit + 文件 hash 失效 | 天 |
| L3 文件级 | 文件职责摘要 | 从索引 + LLM 全自动生成 | 按文件 hash 自动失效 | 天 |

- L1/L2 必须人工把关——这是防"错误上下文"的闸门；电信团队的设计文档文化可直接复用，相当于把文档锚定到代码 hash。
- L3 可全自动，hash 失效率天然局部化：单文件改动只失效一条摘要。
- review 时 diff 落在哪个子系统，注入对应 L1/L2 + 触及模块的 L3，token 花费固定为几百到几千，**与仓库总量解耦**。

### 4.1 什么进 Memory、什么不进

**不进 Memory 的：原始符号关系**（"foo 被谁调用、bar 在哪定义"）。千万行级意味着百万级符号、千万级引用边，物化成文本是 GB 级且需要查询接口——那就成了重新发明索引，还是更差的文本版。这类事实 LSP 一次调用毫秒级有答案，bulk 关系数据留在 clangd 索引里用时现查。

**进 Memory 的：LSP 单查询给不出来的蒸馏产物**。筛选标准三条同时满足：

1. LSP 单查询给不出来；
2. review 高频需要；
3. 变化慢。

普通调用关系第 1 条就不满足，出局；分发表/状态机/全局变量读写清单三条全中，入选。

## 5. 导航图层（L2.5）：内容、提取与分工

> 实施细节另立专项文档：`papers/navmap-libclang-extractor-design.md`（目录结构、数据模型、提取器设计、里程碑）。

### 5.1 四类导航图

1. **消息分发表 / 函数指针注册图**：`g_msgTable[] = {{MSG_1001, handleX}, ...}` → "哪个消息触发哪个 handler"。LSP 只能看到数组初始化，答不了这个映射；review 一个 handler 的第一个问题恰恰是它。
2. **状态机表**：状态 × 事件 → 迁移函数的矩阵。LSP 没有"状态机"概念，只能从初始化器 + 索引推导后固化。
3. **关键全局变量的读写者清单**：`g_sysConfig` 被几百处引用时，`references` 返回的是噪音；review 需要的是"写它的 3 个函数 + 读者按模块分组"——引用列表聚合蒸馏后的产物。
4. **全局状态布局图**：哪个模块拥有哪些全局变量，架构级知识，变化慢。

### 5.2 clangd 的两种形态与 libclang 的分工

建设导航图需要"数组初始化器里第 3 个字段指向哪个函数"这种**内容级**信息，clangd 的两种形态都给不了：索引不存初始化器内容，LSP 协议也没有"展开这张表"的查询。clangd 本质是查询服务，不是批处理提取框架。因此：

| 工具 | 阶段 | 职责 |
|---|---|---|
| `clangd-indexer`（批处理） | 建设 | 产出符号索引分片：定义位置、引用关系。是提取器的"筛子" |
| libclang 提取器（Python `clang.cindex`） | 建设 | 吃同一份 `compile_commands.json`，只解析筛出的候选文件，提取初始化器内容。是"镊子" |
| clangd LSP server | review 查询 | 加载预建索引（`--index-file`），答 definition/references 核对查询 |

三者共享同一份 `compile_commands.json` 与同一个基线 commit。libclang 与 clangd 用同一编译器前端，同一编译参数下 AST 与宏展开结果一致，"提取时看到的"与"查询时看到的"不打架。

### 5.3 自动化提取流水线

核心原则：**索引当筛子，AST 当镊子，绝不做全量 AST 扫描**。

**第 1 步 候选筛选（便宜、全量、分钟级）**：tree-sitter 或正则全仓粗扫疑似分发表的语法模式——全局/静态数组、元素是含函数指针成员的结构体、大括号初始化列表；数组名/注释含 `table`/`disp`/`map`/`hdlr` 词根辅助。这里 tree-sitter 只找候选文件，宏盲点不影响（看错漏看有下一步兜底）。产出候选清单通常几百个文件。

**第 2 步 AST 精确提取（只跑候选文件）**，按产物各一个提取器：

- **分发表**：遍历 `VarDecl`（数组）→ `InitListExpr` → 逐元素提取消息 ID（记录源码宏拼写 `MSG_1001` 而非展开值）+ 函数指针字段（查索引补 file:line）。指定初始化器 `.handler = fn` 与位置初始化都支持。
- **注册式分发**（`RegisterHandler(MSG_X, fn)` 运行期注册）：反向启发式发现注册 API——索引找"参数含函数指针、被调用时传入大量不同函数"的函数，提取其所有调用点参数。注册 API 名单首版人工配十来个，自动发现的候选交人工确认追加。
- **状态机表**：结构同分发表（`{state, event, handler, next_state}` 数组），模板复用。switch 式手写状态机首版不做（电信协议栈表驱动占大头）。
- **全局变量读写者**：索引给出所有引用位置 → 只对引用所在行级位置做 AST 分类（赋值左值/`++`/取地址 = 写，其余 = 读）→ 聚合成"写者函数 Top N + 读者按模块分组"。clangd 索引的 ref 不分读写，故此步必需，但扫描量是引用行级而非文件级。

**第 3 步 增量与产出**：

```
nightly job:
  git diff <上次基线>..HEAD → 变更文件集
    ├─ clangd-indexer 重建变更 TU 的索引分片
    ├─ 变更文件 ∩ 候选清单 → 重跑第 2 步
    ├─ 变更文件实现了 handler → 查 callers 反找表文件 → 相关表重提取
    └─ 全局变量引用文件集变化 → 重做该变量读写分类
  产出: 每张图 JSON + markdown 双格式, 头部标注基线 commit
        未受影响的图原样保留（hash 不变即信任）
```

JSON 供 MCP 工具查询（`lookup_handler(MSG_1001)`），markdown 供 prompt 直接注入；同源生成不漂移。

**第 4 步 兜底与质检**（自动化不可能 100% 覆盖：宏生成表、手写循环注册）：

- **覆盖率指标**：消息枚举中有多少 ID 在提取出的表里有 handler（如枚举 800、表中 600，差的 200 按文件聚类后补提取）。每晚出报告，是质量的量化抓手。
- **一致性校验**：表里每个 handler，用索引确认其 callers 包含表所在文件；对不上即提取错误。
- **LLM 辅助兜底**：确认含注册逻辑但不匹配模板的文件，夜里喂 LLM 提取结构化条目，标记 `source: llm-extracted, unreviewed`，人工抽检转正。只作用于残余小集合，成本可控。
- 顺带产出**死代码信号**：实现了但任何表都未注册的 handler。

工作量估计：分发表提取器核心路径约一个熟练工程师一两周（前提：`compile_commands.json` 已就绪）。首个里程碑做最窄一条：**消息分发表一种产物 + 一个子系统试点 + 覆盖率报告**，跑通再复制到状态机与全局变量。

## 6. Review 时上下文装配流程

针对一个 diff（电信场景通常几十到几百行）：

1. **导航图优先**：plan 阶段先读相关分发表/状态机表，直接得知消息→handler、状态→迁移的映射与文件位置。
2. **LSP 核对**：对导航图指向的关键符号发 2~3 次查询（定义还在不在、签名变没变），而非盲查式探索——LSP 查询量降一个数量级。
3. diff 触及文件 → 查 clangd 索引：被改函数的 callers（行为变化影响面）、被调 callee 的签名/契约。
4. 函数指针/消息分发场景：导航图给出注册点，把注册表条目一并拉出——改 handler 签名没改表是电信 review 最易漏的缺陷类别。
5. 注入该模块的 L1/L2 memory 摘要 + 触及文件的 L3 摘要。
6. diff 命中文件与索引/导航图基线做 hash 比对：stale 区域标注"索引滞后"或降级 grep/全文搜索兜底。
7. 所有注入内容标注来源与基线 commit，让 LLM 区分"编译器级事实""自动提取的导航图"与"可能滞后的摘要"。

## 7. 与现有 OCR 架构的对接点

- `internal/mcp/client.go` 已有 MCP client，外部工具注册进统一 `tool.Registry`（见 `docs/src/overview/concepts.md` §3.5）。clangd 经 mcp-language-server 模式接入、导航图 JSON 封装为 MCP 工具时，对 LLM 与内置六件套工具无差别。
- scan 模板的 `PROJECT_SUMMARY` task 是叙述性 memory 的雏形：把输出从"每次现算"改为"生成一次、commit hash 校验、命中复用"，即为最小 memory 实现。
- Gerrit 工作流已有 `examples/gerrit_ci/` 先例，nightly 索引 job 可挂同一套 CI 基建。

## 8. 落地路线（按风险排序）

1. **验证 `compile_commands.json` 能生成且覆盖率够** —— 电信定制构建系统下这步本身是个项目，是最大风险点，最先做。若卡住（编译数据库出不来或覆盖率低），整体退回 B 计划：gtags/GNU Global 符号索引（精度降级但必能建成）+ memory 为主。
2. 跑通 nightly `clangd-indexer` 增量流程，量化"日变更 → 索引重建"实际耗时与资源。
3. review 侧经 MCP 接 clangd，先只暴露 `definition` / `references` / `documentSymbol` 等三四个查询。
4. 导航图提取首个里程碑：消息分发表 + 一个子系统试点 + 覆盖率报告（见 §5.3）。
5. Memory 从 L2 模块摘要起步，先覆盖变更最频繁的十来个模块，验证注入后 review 质量提升再扩展。
6. 仓库大到增量索引也慢时，再考虑 CRG 式自研图存储（SQLite + 分片）；在此之前 clangd 原生静态索引 + `--index-file` 加载已够用。

## 9. 明确不做的

- **不解析 clangd 索引文件格式自建查询**：批量检查用官方的 `clangd-index-tool` dump，在线查询一律走 clangd/LSP。
- **不依赖 `clangd-index-server`**：remote index 项目已归档。
- **不做全量 Clang AST 扫描**：AST 提取只作用于索引筛出的候选文件。
- **不以 tree-sitter 图为 C/C++ 的主力结构来源**：仅作非 C/C++ 部分（Python/构建脚本等）或索引缺失时的降级补充，以及导航图第 1 步的候选粗筛。
- **CRG 本体不必自研复刻**：其机制（hash 失效、预计算摘要、MCP 投递）已被本文吸收；非 C/C++ 场景可直接引入 CRG 现成实现。

